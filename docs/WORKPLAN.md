# Notchs API: Workplan

Based on *Notchs: Product & Tech Spec v1.0 (October 2026)*. The spec is a working baseline, not final. When something here changes, update this file in the same PR.

This repo (`notchs-api`) holds the backend: FastAPI app, ARQ worker, Alembic migrations. The spec's `backend/` folder is the root of this repo. The Next.js frontend lives in its own repo.

---

## 0. Ground rules for the shared PostgreSQL database

All 4 developers use one hosted Postgres database for development. It is separate from staging and production. Nobody owns it, so it breaks easily. These rules keep it working.

### 0.1 Who changes the schema

| Rule | Detail |
|---|---|
| Only CI migrates the shared `public` schema | A GitHub Actions job (`.github/workflows/ci.yml`, job `migrate-shared-db`) runs `alembic upgrade head` against the shared DB after a merge to `development` (the integration branch). Nobody runs `upgrade` against `public` by hand. |
| Never downgrade | No `alembic downgrade` on shared, staging or prod. To undo a change, write a new forward migration. `downgrade()` functions are still written so local and CI test runs can use them. |
| Linear history | CI fails when `alembic heads` returns more than one head. If two branches add migrations, whoever merges second rebases and re-points `down_revision`. |
| One migration per PR where possible | Easier to review and to rebase. |
| Review autogenerated migrations | Alembic autogenerate misses enum changes, partitioning, grants, partial indexes and check constraints. Read every generated file and fix it by hand. |
| Additive first | Add columns as nullable or with a default. Backfill. Add `NOT NULL` in a later migration. Other developers' running code must keep working while a migration is in flight. |

### 0.2 Testing unmerged migrations: one schema per developer

The spec says migrations reach the shared DB only after merging. Developers still need somewhere to try a migration before merging, so each developer gets a private schema on the same database:

```
public        -> development branch schema, migrated by CI only
dev_<name>    -> each developer's playground (dev_harsh, dev_abhishek, ...)
test_<run>    -> created and dropped by integration test runs
```

- `DB_SCHEMA` env var (default `public`, must be a lowercase identifier). `app/db/session.py` sets `search_path` on connect and also maps unqualified tables to `DB_SCHEMA` (`schema_translate_map`), so ORM queries hit the right schema even through a pooler that drops `search_path`. Raw SQL through the pooler must qualify the schema. Alembic's `env.py` creates the schema if missing and uses it for both the tables and `version_table_schema`.
- To test a branch migration: `DB_SCHEMA=dev_harsh alembic upgrade head`. Drop and recreate your own schema whenever you like. Never touch anyone else's.
- Postgres enum types are per-schema, so they are isolated as well.

### 0.3 Database roles

Two roles, created once by whoever administers the DB:

| Role | Used by | Privileges |
|---|---|---|
| `notchs_migrator` | Alembic (CI and dev schemas) | Owns tables. DDL. |
| `notchs_app` | FastAPI and the worker at runtime | DML on all tables. **`INSERT` and `SELECT` only on `audit_logs`** (spec: append-only). |

Grants are set in migrations so every environment gets the same ones. This needs two URLs: `DATABASE_URL` for the app and `MIGRATION_DATABASE_URL` for Alembic.

**Status on the shared Neon DB: done ✅ (verified 2026-10-10).** Both roles exist on the
`ep-quiet-dew-b36b47cy` endpoint and were created with SQL, not the Neon console (which would
have made them members of `neon_superuser`). They were named `cw_migrator` / `cw_app` until the
Notchs rename and were renamed in place on 2026-10-10; passwords are SCRAM-SHA-256, so they were
unaffected. What each one has:

- `notchs_migrator`: `CREATE` on the database (so Alembic can create `dev_<name>` schemas) and `USAGE, CREATE` on `public`.
- `notchs_app`: `USAGE` on `public`, `statement_timeout = 30s`.
- Default privileges: everything `notchs_migrator` creates later (schemas, tables, sequences) is automatically usable by `notchs_app` for `SELECT/INSERT/UPDATE/DELETE`. `notchs_app` cannot create, alter or drop anything.
- `neondb_owner` is a member of `notchs_migrator` and is used only in the Neon console, never in `.env`.
- Staging and production repeat the same SQL when they are created.

**Watch out: roles are per Neon branch.** They live in the branch's Postgres, not in the Neon
control plane, so a branch created before they existed will not have them and the console's SQL
Editor will report `role "..." does not exist` if it is pointed at that branch. Always check against
the endpoint in your `DATABASE_URL`. Because they were made with SQL, they also do not appear in the
console's Roles tab and their passwords can only be reset with `ALTER ROLE ... PASSWORD`.

**The SQL**, for staging, production, or any new branch that needs them. Generate two strong
passwords and put them in the password manager first, then run this as `neondb_owner` on the
direct (non-pooler) URL:

```sql
CREATE ROLE notchs_migrator LOGIN PASSWORD '<migrator-password>';
CREATE ROLE notchs_app      LOGIN PASSWORD '<app-password>';

-- neondb_owner needs to act as the migrator to set its default privileges below
GRANT notchs_migrator TO neondb_owner WITH ADMIN OPTION;

-- Migrator: owns everything, does all DDL
GRANT CREATE ON DATABASE neondb TO notchs_migrator;      -- lets Alembic create dev_<name> schemas
GRANT USAGE, CREATE ON SCHEMA public TO notchs_migrator;

-- App: runtime only, no DDL
GRANT USAGE ON SCHEMA public TO notchs_app;
ALTER ROLE notchs_app SET statement_timeout = '30s';     -- needed because the pooler drops startup params

-- Anything the migrator creates later is automatically usable by the app.
-- No IN SCHEMA clause, so this covers dev_<name> schemas too, not just public.
ALTER DEFAULT PRIVILEGES FOR ROLE notchs_migrator
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO notchs_app;
ALTER DEFAULT PRIVILEGES FOR ROLE notchs_migrator
  GRANT USAGE, SELECT ON SEQUENCES TO notchs_app;
```

Then: both URLs into the password manager and everyone's `.env`, the
`MIGRATION_DATABASE_URL` repo secret set to the migrator's **direct** URL, and no
`neondb_owner` in any `.env`.

Two things this SQL does **not** cover:

- A table created while connected as `neondb_owner` is not accessible to `notchs_migrator`. Check with
  `SELECT tablename, tableowner FROM pg_tables WHERE schemaname = 'public';` and drop any table owned by
  `neondb_owner` so Alembic recreates it. (On the shared DB this is clean: `alembic_version` is owned by
  `notchs_migrator`.)
- The default privileges above grant `UPDATE`/`DELETE` on every table, including `audit_logs`. The
  migration that creates `audit_logs` must `REVOKE UPDATE, DELETE ON audit_logs FROM notchs_app;` to make
  it append-only as the spec requires. Nothing enforces this yet.

### 0.4 Connections

A shared hosted DB has a low connection limit, and 4 developers, each with hot reload and a worker, use connections fast.

- Keep the SQLAlchemy pool small in dev: `pool_size=2`, `max_overflow=3`, `pool_pre_ping=True`.
- If we connect through a pooler (Supabase/Neon in PgBouncer transaction mode), asyncpg needs `statement_cache_size=0` and `prepared_statement_cache_size=0`. Otherwise it fails at random with "prepared statement does not exist". Setting `DB_USE_POOLER=true` applies both, plus unique prepared statement names. Alembic uses `MIGRATION_DATABASE_URL`, the direct (unpooled) URL.
- Startup settings (`search_path`, `statement_timeout`, UTC) only apply on direct connections. Through a pooler, set `statement_timeout` on the role: `ALTER ROLE notchs_app SET statement_timeout = '30s'`.
- Stop your worker when you are not using it.

### 0.5 Data on the shared DB

- `scripts/seed.py` is **idempotent**. It upserts by natural key (`cities.slug`, `areas.(city_id, slug)`, `venues.code`, `tags.slug`, `badges.code`). It never truncates. It is safe to run any number of times.
- Seed contents: Ahmedabad, 3 areas (e.g. SBR, Prahlad Nagar, Navrangpura), about 6 test venues, the tag list, the first badges, one welcome reward per venue.
- Personal test data uses your own phone number. Do not delete rows you did not create.
- `scripts/reset_me.py --phone +91...` clears your own customer's visits, points and rewards so you can test first-visit flows again.
- The DB URL lives in the password manager. `.env` is gitignored and `.env.example` has placeholders only.

### 0.6 Redis is local and Postgres is shared

Each developer runs their own Redis in Docker, so leaderboards, scan caps and the queue differ per machine while points live in the shared ledger. Provide `python -m app.jobs.cli rebuild-leaderboards` so anyone can rebuild their local Redis from `points_ledger` whenever it drifts.

### 0.7 One WhatsApp test number, one webhook URL

Meta sends webhooks to one URL, so only one developer can receive real messages at a time. To keep everyone unblocked:

- **`POST /dev/simulate-inbound`** (enabled only when `ENV=development`) accepts `{phone, name, text}`, builds a Meta-shaped payload, signs it with the app secret and passes it through the real webhook handler. This is the main way to develop the scan pipeline.
- Real-phone testing uses a tunnel (cloudflared or ngrok). Whoever is using the webhook says so in the team chat.
- Outbound sends go through `WhatsAppClient`. In dev, `WHATSAPP_DRY_RUN=true` logs messages instead of sending them.

### 0.8 Integration tests and CI never touch the shared DB

- CI runs Postgres 18 (same major version as Neon) and Redis as GitHub Actions service containers.
- Locally, `pytest` creates a `test_<uuid>` schema on the shared DB (or uses `TEST_DATABASE_URL` if set), runs migrations, uses transaction-rollback fixtures and drops the schema at the end.

## 1. Schema review: points to settle before the first migration

The spec's schema is solid. These are gaps and Postgres details that will bite if we don't decide them now. Each one should be agreed (or rejected) before Phase 1 ends.

| # | Table | Issue | Proposal |
|---|---|---|---|
| S1 | (missing) | No admin identity. `require_admin` and `audit_logs.actor_type = admin` have nothing to point to. | Add `admin_users (id, name, phone_e164 unique, is_active)` and add `admin` to `auth_tokens.subject_type`. Same magic-link login. |
| S2 | `points_ledger` | `unique (customer_id, reason, visit_id)`: `visit_id` is NULL for quest and trend rows, and NULLs never collide, so duplicates get through. "Once per trend per month" isn't enforced either. | Use partial unique indexes: `(customer_id, visit_id) WHERE reason IN ('new_venue','repeat_visit')`, `(customer_id, reference_id) WHERE reason = 'quest'`, and for trends add a `period_key` text column with `unique (customer_id, reference_id, period_key) WHERE reason = 'trend'`. |
| S3 | `customer_rewards` | Nothing stops a welcome reward from unlocking twice under concurrent scans. | Add `cycle integer default 1` and `unique (customer_id, reward_id, cycle)`. Welcome and quest rewards stay at cycle 1. Punch cards increment it. |
| S4 | `audit_logs` | On a partitioned table the primary key must include the partition key. | PK `(id, created_at)`. Write this migration by hand (autogenerate can't create partitions). Create the first 2 partitions in the migration. |
| S5 | `venue_tags` | "Max 5 per venue" isn't enforceable with a plain constraint. | Enforce in `tags.service` inside a transaction with `SELECT ... FOR UPDATE` on the venue row. Optionally add a trigger later. |
| S6 | `customers` | Handle generation and allowed characters aren't specified. | `^[a-z0-9_]{3,20}$`, stored lowercase, generated as `riya_m`, then `riya_m2`, and so on. |
| S7 | `scan_attempts` | Used for insights (peak hours), so time-range queries matter. | Index `(venue_id, created_at)`. Retention cleanup deletes by `created_at`. |
| S8 | `visits` | Leaderboard and insights filter on `status = counted`. | Index `(venue_id, visited_on)` and `(customer_id, visited_on)`. |
| S9 | `venue_devices` / `auth_tokens` | Device tokens live in `venue_devices.token_hash`, but `auth_tokens.purpose` also has `device_pairing`. | `device_pairing` is the short-lived pairing link. The long-lived device token is `venue_devices.token_hash`. Document this in `venues/models.py`. |
| S10 | Enums | Adding a value later (`ALTER TYPE ... ADD VALUE`) can't be used in the same transaction that adds it. | Rule: a new enum value gets its own migration, and code that uses it ships in a later deploy. |
| S11 | `wraps.share_token`, handles | Public URLs must not be guessable. | `share_token` = 16+ chars from `secrets.token_urlsafe`. |
| S12 | `customers.deleted_at` | Purge job and unique columns: a re-registering phone collides with a soft-deleted row. | Anonymise immediately on delete, which frees the phone number. See [modules/customers.md §6](modules/customers.md#6-delete-my-data), decision D1. |
| S13 | All tables | The spec doesn't say how rows are identified, or what ID people see. | UUIDv7 primary key on every table, plus a `<entity>_code` public code on tables people read. See §1.1. |

### 1.1 IDs and public codes

Every table has two kinds of identifier, with separate jobs:

| Column | Type | Used for |
|---|---|---|
| `id` | UUID (v7), primary key | Foreign keys, joins, internal lookups. Every table has one. |
| `<entity>_code` | `text`, unique, not null | The ID people see: support chats, receipts, admin screens, URLs. Only on tables listed below. |

**Rules**

- **Primary key is always `id`, a UUIDv7.** v7 starts with a timestamp, so inserts land at the end of the index instead of at random places. Generated in Python with the standard library's `uuid.uuid7()` (Python 3.14+, no extra package) via `app/common/ids.py:new_uuid`, so the id is known before flush. `UUIDPrimaryKeyMixin` does this for every model.
- **Foreign keys are `<entity>_id` and always hold the UUID**, e.g. `visits.venue_id → venues.id`. Never point a foreign key at a code.
- **Public code column is `<entity>_code`**, e.g. `venues.venue_code`. Never name it `<entity>_id`; that name belongs to foreign keys.
- **Format: `{PREFIX}-{8 chars}`**, e.g. `VEN-7K3M9QX2`.
  - PREFIX: 3 uppercase letters, one per table, from the list below. Never reused, never changed.
  - The 8 chars are random [Crockford Base32](https://www.crockford.com/base32.html) (`0-9`, `A-Z` without `I L O U`), so `0/O` and `1/I/L` can't be mixed up. 32⁸ ≈ 1.1 trillion codes per table.
  - Random, not sequential: codes can't be guessed and don't reveal how many rows we have.
- **Generated in the app** when the row is created: declare the column as `venue_code: Mapped[str] = public_code_column("VEN")` (`app/db/base.py`), which uses `new_code(prefix)` from `app/common/ids.py`. The column has a unique constraint; on a collision, generate again and retry.
- **Stored uppercase.** Lookups uppercase the input first, so `ven-7k3m9qx2` finds the row.
- **API:** read responses return both `id` and `<entity>_code`. Endpoints that take an ID from a person (admin search, support tools) accept either. Pydantic schemas declare the code as `<entity>_code: PublicCode` from `app/common/schemas.py`, which validates the format.
- **Sequential numbers only where the law or accounting asks for them** (e.g. invoices `INV-000001` from a Postgres sequence). Never show those in public URLs.

**Prefixes** (proposal; agree before migration 0001, then add new tables here in the same PR)

| Table | Column | Prefix |
|---|---|---|
| `customers` | `customer_code` | `CUS` |
| `venues` | `venue_code` | `VEN` |
| `venue_users` | `venue_user_code` | `VUS` |
| `admin_users` | `admin_user_code` | `ADM` |
| `visits` | `visit_code` | `VIS` |
| `rewards` | `reward_code` | `RWD` |
| `customer_rewards` | `customer_reward_code` | `CRW` |

Tables without a code: join tables (`venue_tags`, `visit_tags`), logs and ledgers (`audit_logs`, `scan_attempts`, `points_ledger`, `whatsapp_messages`), tokens (`auth_tokens`), and lookup tables that already have a slug (`cities`, `areas`, `tags`).

**Don't confuse with existing spec columns:** `venues.code` (`KAAFI-SBR`) is the scan code customers type on WhatsApp, and `badges.code` is a badge slug. Both stay as they are; `venue_code` is a separate column.

## 4. Definition of done (every PR)

- Ruff, mypy strict and tests pass in CI.
- New tables or columns come with a reviewed migration. CI shows a single Alembic head.
- The migration was tried in your own `dev_<name>` schema first.
- Routers hold no logic. Business rules sit in services and have unit tests.
- External calls go through their client class and are mocked in tests.
- State-changing actions by venue users and admins call `audit.record()`.
- Conventional commit messages, branch `feature/<short-name>`, PR reviewed.
